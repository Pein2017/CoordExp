# PVCI Step-1 Pre-Commit Probes Design

## Objective

Define the next architecture-routing probe suite for the Qwen3-VL
painted-GT transcription branch. The purpose is to decide what kind of
cursor, if any, is worth internalizing before starting large-scale PVCI,
PICD, selector, coverage, or hidden-state training.

This document is a planning artifact only. It authorizes implementation
planning for the first pixel-side probe wave after user review. It does not
authorize feature-space cursor implementation, hidden-state cursor
implementation, large-scale training, or GPU launch by itself.

## Background

PVCI Step 0 showed that a tight visible mark is a strong causal steering
actuator:

- held-out val100 correct tight mark F1: `0.748340`;
- held-out val100 unpainted same-prompt F1: `0.143558`;
- held-out val100 wrong mark scored against intended target F1: `0.017857`;
- wrong-mark follow analysis: `97.4%` of rows with a prediction followed the
  marked object at IoU >= `0.50`;
- outline-only matched tight outline+center on the val32 coarseness slice;
- loose boxes, center-only marks, and fill-like marks were weak.

This supports the research direction but does not yet resolve the key
architecture fork: the model may be using the mark as object designation, as
direct box-geometry leakage, or as a mixture of both.

## Scope Decision

The approved Step-1 shape is the hybrid option:

1. design the full architecture-routing probe suite;
2. implement only the low-risk pixel-side probes first;
3. use the pixel-side report to decide whether feature-space or hidden-state
   cursor probes are worth implementing.

The first executable wave is:

- **Step 1.1:** existing-output identity-vs-geometry leakage re-score;
- **Step 1.2:** boundary-ablation materialization and inference;
- **Step 1.3:** route-decision report.

Feature-space outline transplant and hidden boundary cursor baselines are
specified as candidate Phase-2 probes, not first-wave implementation work.

## Step 1.1 - Identity Versus Geometry Leakage

The leakage re-score uses existing Step-0 outputs where possible. For each
target row, the primary prediction is the first valid parsed row, because the
probe contract is one marked object should produce one object row. Best-IoU
matching is not used for the primary leakage analysis because it can hide
off-contract multi-row generation.

Required per-row measurements:

- IoU between predicted box and scheduled GT box;
- IoU between predicted box and effective painted mark box;
- L1 distance between predicted box and scheduled GT box;
- L1 distance between predicted box and effective painted mark box;
- whether prediction is closer to GT or closer to mark;
- class or description match separated from localization;
- parse validity and extra-row diagnostics.

Required buckets:

- `tight_outline_center`;
- `outline_only`;
- `box_1p5_outline_center`;
- `box_2p0_outline_center`;
- `grid_snapped_box_outline_center`;
- `center_point`;
- `center_blob`;
- `semi_transparent_fill`;
- any new boundary-ablation variants generated by Step 1.2.

Interpretation:

- prediction closer to loose mark than GT suggests geometry leakage;
- prediction closer to GT than loose or shifted mark suggests designation plus
  visual refinement;
- correct class with poor box suggests identity is available but localization
  refinement is weak;
- wrong class and wrong box suggests the mark variant fails to designate the
  intended instance.

## Step 1.2 - Boundary-Ablation Matrix

The first boundary-ablation execution should run all variants on a compact
`val32` slice. Only variants that are decisive, surprising, or borderline
should be promoted to `val100`.

Core new variants:

- `top_edge_only`;
- `bottom_edge_only`;
- `left_edge_only`;
- `right_edge_only`;
- `top_left_edges`;
- `four_corners_only`;
- `dashed_outline`;
- `inner_outline`;
- `shifted_single_edge`;
- `wrong_aspect_outline`;
- `background_outline`.

Continuity variants from Step 0 remain in the comparison table:

- `tight_outline_center`;
- `outline_only`;
- `box_1p5_outline_center`;
- `box_2p0_outline_center`;
- `grid_snapped_box_outline_center`;
- `center_point`;
- `center_blob`;
- `semi_transparent_fill`.

The first wave should not explore broad style, color, opacity, or thickness
matrices. The research question is boundary geometry dependence, not painter
aesthetics.

## Step 1.3 - Route-Decision Report

The report should avoid brittle hard pass/fail thresholds. It should route
based on effect sizes and stable separations against matched no-mark and
tight-outline controls.

Required report table groups:

- target-row F1, precision, recall, and validity;
- class accuracy or description match;
- mean IoU with GT;
- mean IoU with painted mark;
- mean L1 to GT;
- mean L1 to painted mark;
- closer-to-GT rate;
- closer-to-mark rate;
- wrong/background mark follow rate where applicable;
- malformed, no-prediction, and multi-row rates.

Route criteria:

| Evidence Pattern | Route |
| --- | --- |
| loose or jittered marks produce boxes closer to GT than to the mark | strong PVCI/VCI support; mark behaves like designation |
| loose or jittered marks produce boxes closer to the mark than GT | geometry leakage risk; cursor may need proposal-level precision |
| partial edges or corners preserve most tight-outline behavior | lightweight boundary cursor remains plausible |
| only full tight rectangle works | selector must be boundary-precise before internalization |
| background marks induce confident object rows | verifier, reject, or null-instance selector becomes necessary |
| wrong marks follow wrong object | selector errors should be treated as confident false-positive risks |

The report must label evidence scope as `val32`, `val100`, `proxy`, or
`partial` and must not present target-row F1 as COCO mAP.

## Phase-2 Candidate Probe - Feature-Space Outline Transplant

Feature-space outline transplant is designed but not part of the first
implementation wave.

Candidate contract:

```text
clean image visual/aligner tokens u_j
+ GT-derived edge mask M_edge(j)
+ learnable edge embedding e_edge
-> u'_j = u_j + M_edge(j) * e_edge
```

Matched conditions:

- pixel tight-outline teacher;
- clean image plus GT feature edge mark;
- clean image with no feature mark;
- clean image plus wrong feature edge mark;
- clean image plus jittered feature edge mark.

Initial trainable parameters should be tiny: `e_edge` and, only if needed, a
small renderer or adapter. A positive result means feature-space marks can
replace visible pixel paint without re-running the vision tower per object.

## Phase-2 Candidate Probe - Hidden Boundary Cursor

Hidden boundary cursor is also designed but not part of the first
implementation wave.

Candidate cursor:

```text
cursor_i = MLP([
  mean_inside,
  mean_boundary,
  mean_outside_ring,
  max_inside,
])
```

Candidate injection sites:

- `<|object_ref_start|>`;
- `<|object_ref_end|>`;
- `<|box_start|>`;
- pre-`x1` coordinate position.

Matched conditions:

- correct cursor;
- wrong cursor;
- offset cursor;
- no cursor.

A positive hidden-cursor result with a negative feature-space result would
route toward PICD residual cursor injection rather than visual-feature VCI.

## Non-Goals

- Do not train a new painted teacher in Step 1.1 or Step 1.2.
- Do not compare multiple checkpoints in the first executable wave.
- Do not tune repetition penalty or generation length in the first executable
  wave.
- Do not implement feature-space outline transplant before the pixel-side
  route report.
- Do not implement hidden boundary cursor before the pixel-side route report.
- Do not claim final detection improvement from target-row debug metrics.
- Do not introduce a stable public config schema or artifact contract unless a
  later implementation plan explicitly promotes one.

## Governance

This probe suite is branch-local research scaffolding. The correct carriers
are:

- research notes under
  `research/ideas/qwen3-vl-painted-gt-transcription-probe/`;
- Superpowers design and plan docs under `docs/superpowers/`;
- executable scripts, configs, tests, and artifacts for concrete evidence.

OpenSpec is not required for the first pixel-side wave because it does not
change stable public training, inference, evaluation, or artifact contracts.
If the probe later introduces stable config schema, evaluator semantics,
public artifact names, or reusable model-forward hooks, that later slice
should use OpenSpec before implementation.

## Approval State

The user approved:

- hybrid Step-1 planning: design the full suite, implement pixel-side probes
  first;
- `val32` boundary-ablation first, with selective `val100` promotion;
- frozen Step-0 step-484 checkpoint and decode surface;
- first-valid parsed row as the primary leakage prediction;
- compact decisive boundary variant set;
- effect-size route criteria instead of hard numeric thresholds;
- research note plus Superpowers plan as the carrier, with no OpenSpec for
  the first pixel-side wave.

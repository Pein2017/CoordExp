# CoordExp-Swift Inference Data Parallelism Design

## Context

The existing CoordExp-swift inference baseline owns strict inference config,
Qwen/HF runtime loading, adapter and embedding-delta reload, prompt/image
parity, HF scored generation, compact parsing, selected-token scoring, artifact
writing, and a minimal detection evaluator consumer. That baseline is
recorded in `openspec/changes/build-coordexp-swift-inference-infra/` until it
is archived or synced into stable specs. It is single-process:
`generation.batch_size` controls the number of rows decoded in one HF
`generate` call, but all rows run through one model replica.

This change extends that baseline with data-parallel offline inference. The
goal is to use visible CUDA devices for independent row decoding while
preserving the exact top-level artifact contract consumed by eval.

## Goals / Non-Goals

Goals:

- use all useful visible CUDA devices by default;
- keep `generation.batch_size` as per-device decode batch size;
- avoid DDP/Accelerate complexity for inference;
- bind each worker to exactly one GPU before model loading;
- preserve deterministic row coverage and final row order;
- write rank-local shard artifacts for recovery/debugging;
- strictly merge shard artifacts into the existing top-level artifact names;
- record enough parallelism provenance to make benchmark artifacts auditable;
- keep the shard contract backend-neutral enough for future vLLM.

Non-goals:

- no vLLM implementation in this change;
- no tensor/model parallelism;
- no distributed collectives;
- no CPU fallback for inference execution;
- no metric reduction inside `src.infer`;
- no public stable CLI GPU-id surface;
- no change to prompt, parsing, scoring formula, or evaluator metric semantics.

## Decisions

### Controller And Worker Shape

The public entry remains:

```bash
python -m src.infer --config CONFIG.yaml
```

The top-level process acts as a controller when more than one active rank is
needed. It resolves config, creates the run directory, writes canonical
top-level resolved config artifacts before worker launch, computes the shard
plan, launches workers, waits for all workers, and strictly merges shard
artifacts. `configs/resolved.json` and `configs/resolved.yaml` are run-level
evidence, not row artifacts, and are not regenerated by merge.

Workers are fresh-interpreter subprocesses, not forked Python workers and not
DDP ranks. The controller should launch a private module entrypoint such as
`python -m src.inference.worker` with resolved config, shard plan, rank, and
shard output arguments. This internal surface is not a stable user CLI.

Worker execution uses a reusable shard primitive split out from the current
single-process pipeline. The primitive receives an already resolved config, an
assigned row subset or shard-plan slice, a fixed shard output directory, and
worker metadata. It must not re-resolve collision-policy run directories, must
not process unassigned rows, and must not publish canonical top-level artifacts.

Rationale: inference rows are independent. Subprocess workers give clean CUDA
state, clean logs, and simple failure boundaries without requiring distributed
training infrastructure.

### CUDA Device Binding

The controller discovers the parent visible CUDA device tokens. If
`CUDA_VISIBLE_DEVICES` is set, those tokens are the resource boundary. If it is
unset, the controller may discover CUDA device count and synthesize tokens
`0..N-1`.

Each worker is launched with exactly one assigned token:

```text
CUDA_VISIBLE_DEVICES=<assigned-token>
```

Inside each worker, the only supported runtime device is logical `cuda:0`.
Workers must validate that CUDA is available and that exactly one CUDA device is
visible before model loading. The implementation must not rely on every helper
using `cuda:{local_rank}` correctly; per-worker visibility isolation is the V1
safety mechanism.

Rationale: the current runtime and Qwen loader use generic CUDA placement with
`device_map=None`. Narrowing the environment makes plain `cuda` and `cuda:0`
mean the assigned GPU, avoiding silent all-ranks-on-GPU0 failures.

### Active Rank Count

The controller computes decode batches from the full ordered input row list:

```text
decode_batch_size = generation.batch_size
num_decode_batches = ceil(num_rows / decode_batch_size)
active_ranks = min(num_visible_cuda_devices, num_decode_batches)
```

If `active_ranks == 0`, inference fails fast because empty input is not a
benchmark-meaningful run. If `active_ranks == 1`, the implementation may keep
the existing direct single-process path, but this direct path is still a
non-dry inference execution path and therefore must require CUDA before Qwen
model loading. If `active_ranks > 1`, it uses shard workers and strict merge.

Rationale: launching model replicas for ranks with no decode batch wastes memory
and time. “Use all GPUs by default” means use all useful visible GPUs.

### Row Sharding

Rows are first grouped into decode-batch blocks of up to
`generation.batch_size` rows. Blocks are assigned round-robin to active ranks.
The parent records a shard plan containing row indices, row ids, batch ids,
rank assignments, per-device batch size, and a shard-plan fingerprint.

Rationale: batch-block round-robin is deterministic, simple, preserves the
meaning of per-device batch size, and balances batch count better than one
contiguous chunk per rank. Final top-level artifacts are sorted back to original
`row_index`.

### Shard Artifacts And Merge

Each worker writes a complete rank-local artifact set under:

```text
run_dir/shards/rank-XXX/
```

Rank-local artifacts follow the same schema as single-process output, but only
cover the rows assigned to that rank. A worker manifest records rank, world
size, assigned parent-visible device token, worker `CUDA_VISIBLE_DEVICES`,
normalized logical device `cuda:0`, `torch.cuda.device_count()==1`,
`torch.cuda.current_device()==0`, model first-parameter device after load, row
coverage, generation policy, model/tokenizer/processor identity, adapter
identity and status when present, embedding-delta identity and load status when
present, and shard artifact hashes.

After all workers exit successfully, the controller merges row artifacts into
the canonical top-level files expected by eval:

```text
gt_vs_pred.jsonl
gt_vs_pred_scored.jsonl
gt_vs_pred_scored.jsonl.provenance.json
pred_token_trace.jsonl
parse_diagnostics.jsonl
image_plan.jsonl
summary.json
run_manifest.json
```

The required rank-local set is the scored inference artifact family:
`gt_vs_pred.jsonl`, `gt_vs_pred_scored.jsonl`,
`gt_vs_pred_scored.jsonl.provenance.json`, `pred_token_trace.jsonl`,
`parse_diagnostics.jsonl`, `image_plan.jsonl`, `summary.json`, and
`run_manifest.json`. Worker shard directories may also copy or link resolved
config evidence, but the canonical resolved config remains top-level.

The merge is strict. It fails before writing benchmark-looking top-level scored
artifacts if any worker fails, any required shard artifact or manifest field is
missing, row coverage is incomplete, row ids are duplicated, row order is
inconsistent, trace replay is incomplete, selected-token scores cannot be
recomputed from merged trace evidence, or identity fingerprints disagree across
shards. The identity vector includes base model, adapter status/active adapter,
embedding-delta load identity, tokenizer, processor, prompt/template and object
ordering, dataset, generation/decode policy, parser policy, score policy,
raw/scored SHA binding, row-count/row-identity binding, and row-local
`pred_score_source` / `pred_score_version` preservation.

Merged `gt_vs_pred_scored.jsonl.provenance.json` is regenerated after merge and
is the evaluator-sidecar source of truth. `run_manifest.json` may duplicate or
summarize shard metadata, but it does not substitute for the scored provenance
sidecar. Merge output is staged, validated as a complete top-level artifact
family, and then published atomically. On merge failure, the controller preserves
shard directories and writes only terminal root status evidence with
`benchmark_eligible: false`.

### Backend Boundary

V1 data-parallel execution is HF-only. The worker interface should be
backend-neutral in data shape: worker input is assigned rows plus resolved
config, and worker output is a validated artifact set plus manifest. A future
vLLM implementation may use the same shard plan and merge contract, but this
change must not implement vLLM or mark vLLM acceptance complete.

### CUDA Missing Behavior

CUDA is required for every non-dry inference execution path. If no CUDA devices
are visible, inference fails before model loading. Dry-run remains a config and
run-directory validation path and does not require CUDA or model loading. CPU
debug fallback is intentionally out of scope for this feature.

## Risks / Trade-offs

- Worker logs and shard artifacts can make the run tree larger. This is
  accepted because shard evidence is valuable for benchmark trust and debugging.
- Subprocess launch has more boilerplate than a direct in-process loop. This is
  accepted because it avoids CUDA/fork hazards and device-binding ambiguity.
- Batch-block round-robin may not perfectly balance heterogeneous image/prompt
  lengths. It is chosen for V1 simplicity and determinism; length-aware
  scheduling can be a later optimization if profiling proves imbalance.
- Strict merge may fail a whole run after most rows decode successfully. This is
  intentional for metric-bearing artifacts. Shard directories remain available
  for diagnosis.

## Migration Plan

1. Add data-parallel planning and CUDA-discovery helpers with unit tests.
2. Split a reusable shard execution primitive from `pipeline.run`, with fixed
   shard output directory semantics and no top-level canonical writes.
3. Add private worker launch/binding surfaces and worker-local CUDA validation.
4. Teach the pipeline to choose direct single-process versus controller/worker
   execution.
5. Add shard artifact writing and strict merge validation.
6. Extend manifests/provenance with parallelism metadata.
7. Add targeted tests and one real two-GPU HF smoke before production
   data-parallel benchmark claims.

## Open Questions

No user-blocking design questions remain after the grill decisions. Future
implementation may expose a private test override for visible-device discovery,
but it must not become a stable public config or CLI surface in this change.

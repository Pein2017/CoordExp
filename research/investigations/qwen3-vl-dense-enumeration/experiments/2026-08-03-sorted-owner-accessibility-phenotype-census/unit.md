### Estimand name and semantics

The primary spatial estimand is **category-field support at owner geometry**:
the complete coordinate-sequence log likelihood of a candidate box, conditioned
on a native context and on a *forced category query*, never on that owner's
identity. It is a category-conditioned score evaluated at an owner's geometry.

It is **not** a per-owner proposal probability, and no artifact, field name,
figure, or sentence may present it as one. Proposal quantities are only ever
emitted per context and per category, never per owner (contract item 9).

Proposal surface and coordinate localization are separate measurements with
separate schemas. A weak boundary gate is not evidence that a description is
inaccessible, and a strong localization score is not evidence that the model
would ever propose that category.

## Context registry and the canonical query suffix

For each image the registry contains boundary indices `0 .. R`, where `R` is
that image's native complete row count:

- boundary `0` is `root` (`context_role = "root"`, prompt only);
- boundary `k` for `0 < k < R` is `row_boundary`, whose prefix is the literal
  prompt plus native complete rows `0 .. k-1`;
- boundary `R` is `terminal`, carrying `terminal_kind` from the rollout stop
  reason (`natural_stop` for `im_end`, `length_truncated` for a length stop,
  `other` otherwise).

Prefixes are the exact generated token IDs. Rows are never re-parsed,
re-serialized, or re-tokenized, and **no forced-continue row ever enters a
prefix**: this registry is built only from natively generated complete rows.

Each context seals `prompt_token_ids_sha256`,
`generated_prefix_token_ids` and its digest,
`observed_self_prefix_token_ids_sha256`, the ordered canonical prediction row
IDs, `image_id`, `context_role`, `terminal_kind`, and `loop_tail`.

### Canonical coordinate-query suffix (contract item 5)

For a context `c` and a normalized description `d`, the query group `(c, d)`
has the literal reforward prefix

`full_prefix = observed_self_prefix(c) + [OBJECT_REF_START, tokens(d), OBJECT_REF_END, BOX_START]`

and nothing else.

The suffix is **variable length**: `person` contributes one description token
(suffix length four) while `dining table` contributes three (suffix length
six). The assertion is therefore **exact tail equality against that category's
sealed suffix**, plus a final `BOX_START` — never a fixed "last four tokens"
check, which would pass a truncated multi-token category. The planner and the
scorer both assert that `full_prefix[-1] == BOX_START` and that
`full_prefix[-len(suffix):]` equals the sealed suffix for that exact category.

The prefill logits must already *be* the `x1` distribution, which holds only
when the prefix ends at the forced box opener. A prefix ending at a prior
`box_end` silently asks "what comes after a finished row" instead of "what
coordinate opens this forced box". Any mismatch is a hard, fail-closed error,
never a warning and never a fallback.

All scores produced before this correction ("pre-P0") are quarantined. The
scorer accepts no score artifact as input; it consumes only the sealed plan.

### Category token identity

`tokens(d)` is derived, per description, from the exact native token span
observed in the greedy rollout wherever that description was emitted; all `32`
observed descriptions have a single uniform observed span. Exactly two GT
descriptions -- `bicycle` (image `5001`) and `bowl` (image `13923`) -- are
never natively emitted and are resolved by the production tokenizer. That
fallback is validated by re-encoding all `32` observed descriptions and
requiring exact agreement with their observed spans (verified: `0` mismatches).
Each category row records `token_source` as `observed_native_row` or
`tokenizer_encode`. An unresolvable category blocks only its own query groups
and is recorded, never guessed.

### Loop marking: continuous counts first, flag second (frozen, score-independent)

Loop marking is derived only from the exact native generated token spans. It
reads no score. Every boundary records three **continuous, auditable**
quantities describing the last complete row in its prefix (all null at `root`,
which has no such row):

- `prior_identical_row_count` -- the number of earlier rows in the same image
  whose exact generated token span equals this row's;
- `consecutive_identical_row_run_length` -- the length of the run of
  consecutive identical rows ending at this row (`1` when the previous row
  differs); and
- `repeated_raw_span_sha256` -- the digest of the repeated raw span when
  `prior_identical_row_count > 0`, else null.

The convenience flag `loop_tail` uses one frozen literal rule,
`consecutive_identical_row_run_length >= 3`, and nothing else.

The flag is a bookkeeping convenience for aggregation weighting. It is **not a
mechanism label**: nothing may be described as "looping", "degenerate
decoding", or "repetition collapse" on the strength of the flag. Analysis
retains and reports the continuous counts, and any statement about repetition
must cite them.

Measured on the frozen rollout, both the continuous counts and the flag isolate
exactly two images:

| Image | Rows | Max consecutive run | Boundaries with run `>= 3` | Rows with `prior_identical_row_count > 0` |
| --- | --- | --- | --- | --- |
| `4134` | `147` | `16` | `51` | `68` |
| `14038` | `88` | `14` | `31` | `40` |
| all other ten | -- | `1` | `0` | `0` |

So `82` of `412` contexts carry `loop_tail = true` and `330` do not.

## Score-independent candidate bank (contract item 7)

Every owner contributes exactly **seventeen logical transform roles**, in a
fixed order, generated before any score is read, from the owner's ledger box
and its own size. With owner width `w` and height `h` in decoded pixels,
`dx = max(1, round(w / 4))` and `dy = max(1, round(h / 4))`.

**Core (9)** -- compatible with the all-person precedent:
`exact_gt_anchor`; `translate_left`, `translate_right`, `translate_up`,
`translate_down`; `width_expand`, `width_shrink`, `height_expand`,
`height_shrink`.

**Extension (8)** -- exactly:
`translate_up_left`, `translate_up_right`, `translate_down_left`,
`translate_down_right`; `isotropic_expand`, `isotropic_shrink`,
`top_anchored_height_shrink`, `bottom_anchored_height_shrink`.

The role list is fixed and total. There is no reserve list, no substitution,
and no score-selected replacement.

### Physical candidate identity and cross-owner collapse

Roles are converted to coordinate tokens with the production per-image
pixel-to-bin conversion. A role is `admitted` only when its clipped pixel box
is valid and its bins do not collapse; otherwise it is recorded with an
`invalid_reason` and contributes no scored row.

A **physical candidate** is identified by
`digest(image_id, normalized_description, coord_token_ids)` — deliberately
*not* by its generating owner. Admitted roles collapse by exact
coordinate-token identity **within `(image, normalized_description)`, across
owners**: if two same-category owners realize the same coordinate tuple, that
is one physical candidate, scored once and contributing one rank mass, with
both generators retained in a provenance list
(`{generator_gt_owner_id, logical_transform_role}`, plus
`generator_owner_count` and `cross_owner_generated`).

Generator provenance never enters identity, rank, or assignment. Each query
group contains exactly one request per unique coordinate tuple; a duplicate is
a fail-closed contract violation, not something to dedupe quietly. A native or
free-decode sidecar whose tuple is identical to a bank candidate's joins that
candidate's provenance and never adds a second rank mass.

#### Candidate-versus-generating-owner geometry

Every admitted logical role, and every generator entry on every physical
candidate, carries deterministic geometry measured on the **decoded** candidate
box (after the pixel-to-bin-to-pixel round trip, i.e. the box the model is
actually asked about) against that generator's own GT box:
`intersection_over_union_with_generator`, `center_offset_pixels`,
`extent_ratio`, `candidate_extent_pixels`, `generator_extent_pixels`,
`candidate_area_pixels`, `generator_area_pixels`, `area_ratio`, and the
`generator_bbox_pixel_xyxy` it was measured against.

Geometry is **per generator, not per candidate**. After cross-owner collapse
one physical candidate may have several generators with different GT boxes, so
the same coordinate tuple has a different IoU and centre offset for each of
them; attaching geometry to the candidate would silently attribute one
generator's numbers to all of them. `generators` is authoritative;
`representative_generator_geometry` is an explicitly-named single-row summary
that always names the generator it came from.

These fields are score-independent plan facts. Downstream analysis consumes
them and does not re-derive them. As a worked check, `isotropic_expand` with
`dx = w/4`, `dy = h/4` per side yields `extent_ratio = [1.5, 1.5]`,
`area_ratio = 2.25`, and IoU `1/2.25 ~ 0.444` — the figure quoted in the bank
adequacy rationale.

### Owner support: generator-local landscape versus strict assignment

An owner's **primary neighbourhood is its generator-local landscape**: the
physical candidates it generated, minus any candidate strictly assigned to a
*different* owner (those are excluded from its support and moved to the
collision diagnostic).

Strict assignment is a **separate, narrower, owner-identifiable lower bound**,
not bank membership. Candidates are partitioned per owner as:

| Partition | Enters `L` | Enters `U` |
| --- | --- | --- |
| `strict_assigned_self` | yes | yes |
| `ambiguous_upper` | no | yes |
| `unmatched_generator_local` | **no** | **yes** |
| `other_owner_strict` | no | no (excluded; collision diagnostic) |
| `not_generated_by_owner` | no | no |

`unmatched_generator_local` is the partition for a perturbation that was
*designed* to move off its own owner and so fails the `0.5` matcher. It is
still part of the owner's landscape, so it enters the upper bound `U` — but it
is **not** owner-identifiable, so it never enters the lower bound `L`. Any
disposition that flips between `L` and `U` is reported `unresolved`.

Every `(owner, context)` reports at minimum `generator_local_max`,
`generator_local_max_excluding_other_owner_strict`, `strict_assigned_max`,
`exact_anchor_score`, and `ambiguous_upper_max`. Every owner reports
`distinct_physical_candidate_count`, `uniquely_assigned_candidate_count`, and
`other_owner_strict_count`.

**Rank and margin are routing and competition quantities only.** They describe
which candidate or owner won a query group. They are *not* a support
criterion: nothing in this unit may read "rank `1`" as evidence that an owner
has localization support, and no disposition is derived from a rank. Support is
defined solely by the calibrated local-peak statistics below. Competition ranks
use exclusion-filtered generator-local maxima; the strict table is parallel only
and never the primary rank.

### Support definition: calibrated local peak

Support is a property of the *shape* of an owner's local landscape, not of its
position in a ranking. Two continuous statistics are computed per
`(owner, context)`, both on
`generator_local_max_excluding_other_owner_strict`:

**`peak_lift`** — the owner's best candidate log posterior within the *unique*
`(context, category)` candidate population, minus `log(1 / N_unique)`:

```
peak_lift = best_logprob
          - logsumexp(all unique candidate logprobs in the same query group)
          + log(N_unique)
```

It measures how sharply the category's coordinate mass concentrates on this
owner's geometry relative to a flat distribution over the whole group. It is
`0` for a uniform group and at most `log(N_unique)`, and it is invariant to
adding a constant to every logprob. It is **not** the best minus an
owner-local reference level.

**`local_concentration`** — the owner's best exclusion-filtered
generator-local score minus the **median** of that owner's own
exclusion-filtered bank scores (the mean of the two central values for an
even-sized bank):

```
local_concentration = best exclusion-filtered generator-local score
                    - median(that owner's own exclusion-filtered bank scores)
```

Its reference population is the owner's own bank, so a crowded image cannot
depress it through competition the owner never had to win. It is an unbounded
log-space gap, **not** a normalized-mass share.

#### Usable support is a conjunction

An owner has usable support in a context, under a given ambiguity bound, when
**both** statistics clear their frozen threshold by at least `epsilon`:

```
usable_support = peak_lift            >= t_peak + epsilon
             AND local_concentration  >= t_conc + epsilon
```

Sitting exactly on a threshold is not support.

#### Threshold calibration (TP-calibrated, discovery only)

Thresholds for both statistics are calibrated on **discovery true-positive
owners at the deterministic due boundary** — owners the native greedy route
actually emitted, at their own due context. True positives are the calibration
population precisely because their localization is not in question.

- **Primary:** the fixed quantile `q = 0.10` of the discovery-TP distribution
  of each statistic. An owner has support when both statistics meet their `q10`
  threshold.
- **Sensitivity only:** `q = 0.05` and `q = 0.25` are reported as sensitivity
  bands. They never replace the primary threshold and never define a
  disposition.
- **Primary stratification:** pooled over all discovery TP owners.
  Category-stratified thresholds are **diagnostic only**.
- **Fallback to pooled:** a stratum with fewer than `20` calibration true
  positives, or whose `q10` lies within `epsilon` of the stratum minimum
  (a degenerate quantile), falls back to the pooled threshold. A category with
  fewer than `20` calibration TPs is flagged `pooled_underrepresented` and
  **never** receives a changed threshold.

Every threshold is a fixed quantile of a frozen population. There is no search,
no tuning, and no threshold that depends on an outcome.

### Numerical tolerance

Two fixed epsilons are frozen before capture:

| Quantity | `epsilon` |
| --- | --- |
| Single-context support decisions | `0.002` |
| Cross-context deltas | `0.004` |

These are **fixed constants, not adaptive**. Observed run-to-run parity from
the scalar reference probes is a *compliance check against* these bounds: if
observed parity is worse than the bound the affected rows fail admission. A
tighter observed parity never shrinks `epsilon`, and a looser one never
enlarges it.

### Frozen bank adequacy rule

Adequacy is measured on `distinct_physical_candidate_count` after collapse,
with the exact anchor mandatory. Frozen before any score:

| Status | Condition | Disposition eligibility |
| --- | --- | --- |
| `full` | exact anchor uniquely self-assigned and all `17` distinct candidates | eligible |
| `adequate_reduced` | exact anchor uniquely self-assigned and `12`–`16` distinct (`>= 70.6%`) | eligible |
| `undercovered_unresolved_only` | fewer than `12`, or exact anchor missing or not uniquely self-assigned | floored to `unresolved` |

Adequacy is deliberately **not** measured on unique assignment. The bank is a
local landscape probe, not a set of alternative detections: an isotropic
expansion by `dx` per side has IoU `1/2.25 ~ 0.44` with its own generator and
correctly fails the `0.5` matcher. Measured on the frozen panel the dominant
loss is `unmatched` (`2119` roles) rather than same-category competition
(`other` `163`, `ambiguous` `0`), and owners that are the only instance of
their category in their image show the same distribution. Keying adequacy on
unique assignment would mark `330` of `346` owners undercovered and neuter the
census; keying it on distinct candidates yields `338` `full`, `8`
`adequate_reduced`, and `0` floored.

An owner is never floored merely because a few transforms produced
token-identical boxes, and never for a reason that would license borrowing
another owner's candidates or growing the bank mid-run.

### Sidecars

Native emitted boxes (the `400` greedy rows, bound to their canonical
prediction row IDs) and exactly one free greedy box per `(context, category)`
are sidecars. They are recorded, they are used for finite-bank undercoverage
diagnosis, and they are excluded from every core rank, margin, and competition
statistic.

## Frozen measurements

### Localization (contract item 8)

Per scored request the run preserves: per-coordinate selected log
probabilities for `x1, y1, x2, y2`; the `box_end` continuation where
applicable; top-k token alternatives at each coordinate; the candidate's
`exact` / `neighborhood` / `extension` provenance; same-description competition
rank and margin within the query group; and overlap, IoU, center-offset, and
extent fields against the generating owner.

The complete `1000`-bin `x1` distribution at the canonical suffix is stored as
a diagnostic only. It is never rendered or interpreted as a 2-D heatmap, and it
never enters a rank.

Raw log probabilities are never compared across images. Every cross-image
statistic uses within-context normalized or rank-based quantities.

### Proposal surface (contract item 9)

Three named quantities are kept **separate** in the schema and are never
conflated:

- **(a) `boundary_gate`** -- at the natural boundary position (the end of
  `observed_self_prefix`, with nothing forced), the logits and probabilities of
  `OBJECT_REF_START` (continue) versus `IM_END` (stop). This is a gate. It is
  never described as description accessibility.
- **(b) `category_routing_event`** -- conditional on a forced
  `OBJECT_REF_START`, the raw sequence sum of log probabilities over
  `[tokens(d), OBJECT_REF_END]`, for every normalized description present in
  the image, plus its within-context rank. Raw sequence sum only; never a
  per-token mean.
- **(c) `row_prefix_block`** (optional) -- the raw sequence sum over the full
  `[OBJECT_REF_START, tokens(d), OBJECT_REF_END, BOX_START]` block.

No coordinate score enters any proposal quantity, and no proposal quantity is
emitted per owner.

The free decoded next row per context is recorded alongside, as behavior, not
as a probability.

### Frontier conditioning (contract item 6)

For each `(owner, context)` the analysis records the signed ordinal and signed
pixel distance from the owner sort key `(y1, x1)` to the context frontier (the
last complete emitted row's sort key), the count of remaining same-description
owners ahead of that frontier, `has_been_passed`, and the context role.

Owner summaries carry:

- `best_over_all_contexts` -- **diagnostic only**, because context counts range
  from `7` to `148` and are dominated by the two loop-degenerate images;
- `best_non_loop_context` -- best over non-loop-tail contexts;
- `minimal_frontier_distance_context` -- the context minimizing absolute
  frontier distance, with its measurements; and
- `loop_tail_only_support` -- support present only in loop-tail contexts, kept
  as a separate field and explicitly **not** evidence that the ordinary route
  made the owner accessible; and
- `tested_context_count` and `non_loop_context_count` -- how much evidence the
  owner actually has, so a summary can never look equally supported at `7`
  contexts and at `148`.

Ties for `minimal_frontier_distance_context` are broken by one frozen rule:
the **first non-loop boundary attaining the minimal absolute signed distance**,
in ascending boundary order. No tie is ever resolved by looking at scores.

Phenotype and confirmation rules are owner-level and consume only the frozen
`best_non_loop_context` and `minimal_frontier_distance_context` summaries.
`best_over_all_contexts` never enters a rule.

An owner never observed within the frozen frontier window in any admitted
context is labelled `never_frontier_tested`. It is never labelled
`persistent_no_tested_localization_support`, and its absence of support is
never reported as a negative result.

### Who may close as a persistent negative

Three eligibility floors sit in front of the statistical test. All three must
lift, and an owner blocked by any of them closes `unresolved` instead. Blocked
owners are **still fully censused** — they keep every continuous row, their
full seventeen-role bank, and every measurement — they simply cannot carry a
negative conclusion and never enter a false-negative prevalence or confirmation
denominator.

| Floor | Blocked population | Why a negative would be an artefact |
| --- | --- | --- |
| `greedy_eligible` | the `3` `globally_ambiguous_neutral` owners (`gt:14038:41/42/43`) | they have no unique identity under the canonical matcher, so "this owner was not localized" is not a statement the census can make about them |
| `native_false_negative` | the `141` native true positives | they are the calibration and positive-control population that *defines* the `q10` threshold, so roughly a tenth of them sit below `q10 + epsilon` by construction; labelling those as persistent negatives would be circular and would mix the calibration population into the quantity being estimated |
| adequate bank | owners with `undercovered_unresolved_only` banks | an undercovered bank cannot support a negative conclusion about geometry it never probed |

On the frozen panel that leaves `346 - 141 - 3 = 202` owners eligible to close
as persistent negatives, which is also the false-negative denominator.

A `persistent_no_tested_localization_support` disposition therefore requires
**all** of: `greedy_eligible`; `native_false_negative`; frontier-tested;
non-loop primary contexts; an adequate distinct bank (`full` or
`adequate_reduced`); the exact-anchor score reported; and

```
not any(context: peak_lift_U >= t_peak + epsilon
            AND local_concentration_U >= t_conc + epsilon)
```

— that is, **no** tested context in which *both* statistics clear under the
optimistic `U` bound. Anything short of that is `unresolved`, and a low rank is
never part of the test.

The quantifier placement matters. It is **not** "each statistic is individually
below its threshold in every context": an owner could clear `peak_lift` in one
context and `local_concentration` in another, never clearing both at once, and
would still be a persistent negative under the correct rule while the wrong
per-statistic reading would call it supported.

## Discovery, confirmation, and promotion

Continuous owner-level features are computed first, over all `346` owners, in
both halves. Cohorts are derived second, and only on the discovery half.

### Blind capture: all twelve shards may be front-loaded

Capturing a confirmation shard does not spend it, because analysis order is
enforced by a **blind hash-DAG** rather than by capture order. All twelve raw
shards may therefore be captured before any analysis runs, which is what lets
GPU capture be front-loaded and the GPUs released.

The DAG has four stages, each binding the previous stage's digest:

1. **Capture manifest first.** Before any analysis, a manifest seals every
   shard's raw digests. Confirmation shard digests are recorded here and are
   not read again until stage 4.
2. **Calibration consumes discovery digests only.** The TP threshold
   calibration reads discovery shards exclusively. It cannot read a
   confirmation row, so no confirmation outcome can influence a threshold.
3. **Calibration receipt sealed.** The frozen thresholds, their population,
   the `q10` primary, the `q05`/`q25` sensitivity bands, the pooled fallbacks,
   and any `pooled_underrepresented` flags are sealed with a digest.
4. **Confirmation binds the exact calibration receipt.** Confirmation analysis
   refuses to run against any calibration receipt whose digest differs from the
   sealed one. There is no retune, no re-derivation on all twelve images, and
   no second calibration pass.

Blindness is a property of the DAG, not of the operator's discipline: a
confirmation number cannot reach a threshold because the threshold was already
digest-sealed before confirmation rows were opened.

The discovery half `[10707, 14038, 2685, 5001, 6040, 7511]` is where any
phenotype rule -- its features, thresholds, and directions -- is chosen and
then **frozen with a digest**. The confirmation half
`[13348, 13923, 14439, 1584, 16228, 4134]` is scored by applying that frozen
rule object unchanged. The merge tool binds the discovery rule digest into the
confirmation report and refuses to run confirmation against any rule object
whose digest differs. There is no confirmation threshold or rule tuning, and no
"re-derived on all twelve images" variant is admitted.

A phenotype may be promoted to a causal proposal only when it (a) survives
confirmation under the frozen rule, (b) covers at least `15` false-negative
owners across at least `4` images, and (c) carries a preregistered directional
intervention prediction written before the intervention is designed. Promotion
is a separate authorization; this unit does not perform it.

## Execution architecture (contract item 10)

GPU capture is front-loaded across twelve independent per-image shards and then
released. There is **no serial two-image gate** and no global serial
calibration gate.

- The CPU planner runs first and completely. It emits immutable JSONL
  registries, per-shard manifests, digests, and a sealed `capture-rules.json`,
  and it allocates no run ID until the plan is executable.
- Each shard covers exactly one image and is independently launchable. Shards
  carry `estimated_work_units` so an eight-GPU queue starts largest-first:
  `4134` and `14038` dominate (`92,648` and `71,111` of `246,067` physical
  candidate rows) and must be dispatched first.
- One long-lived model/session per image shard; query groups execute
  **sequentially** within it. This avoids 412 model loads without sharing any
  admission.
- A shard scores a deterministic scalar uncached reference subset, selected
  from request-ID digests and never from scores or owner identity, and records
  finite, token-alignment, argmax, and scalar-versus-reference checks with
  numeric bounds.
- A shard-local failure quarantines that image only. More than two quarantined
  images is a global stop declared by the merge tool.
- An ambiguous close decision may request a scalar overlay for the affected
  rows; that request is recorded and does not gate other shards.

Evidence from a failed or quarantined shard is never used.

### Admission channels and exact-prefix identity

For the first capture, accuracy is chosen over efficiency: admission identity
is the **exact prefix digest**, not a suffix-shape class. The runtime's
existing admission identity already includes the exact prefix, and no proof
exists that admission is invariant under token identity at equal shape.
Suffix-shape sharing is therefore rejected.

Three channels are separately admitted, and no admission ever covers another:

| Channel | Scope | Keyed on |
| --- | --- | --- |
| `query_suffix` | per `(context, category)` | observed prefix + canonical query suffix |
| `proposal_boundary_gate` | per context | observed prefix only (nothing forced) |
| `proposal_category_route` | per `(context, category)` | observed prefix + routing-path digest |

The proposal routing path is exactly
`[OBJECT_REF_START, category tokens, OBJECT_REF_END]` and deliberately stops
before `BOX_START`, because no coordinate score may enter a proposal quantity.
Two categories in one context traverse different token identities and lengths,
so one context-level observed-prefix receipt does **not** cover their routes.

Every score row references its covering `admission_receipt_id`, and the merge
fails any row whose covering receipt is absent. Admission is re-run
independently and is never inherited across contexts, categories, or channels.

Bulk scoring runs on the admitted KV-cache path. Batched full reforward does
not reuse the image prefix and is a parity/fallback diagnostic only.

### Hard Qwen3-VL runtime invariants

The model carries a shared mutable `rope_deltas`, so an implicit-position call
silently corrupts positions for every other group on the same model object:

- every model call passes explicit, non-`None` `position_ids`;
- `model.generate()` and any raw call that does not preserve explicit positions
  are forbidden on the scoring model;
- no concurrent group threads on one model; groups run sequentially;
- a fresh `DynamicCache` per query group, asserting
  `cache_length == prefill_length`; and
- the group backend is deleted before the next group starts.

### Representative smoke

The representative real-model smoke runs on image **`6040`**, the smallest
*discovery* shard (`15` owners, `4` categories, `11` contexts, `2,772`
candidate rows). It is deliberately not a confirmation image: spending
held-out evidence on a smoke would compromise the confirmation half before its
rule is even frozen.

### Deferred robustness

Only repetition-penalty stratum `1.0` is scored. An `rp1.10` robustness view is
**deferred, not blocking**: no canonical `rp1.10` native rollout artifact is
frozen for this panel, so there is no admissible context registry to score it
against.

## Stop rules

Stop or narrow before interpreting any census feature if:

1. checkpoint, adapter, special-token delta, panel, prompt, tokenizer, matcher,
   owner-ledger, prediction-row-ledger, or greedy-rollout identity differs from
   the frozen source boundary;
2. the owner ledger does not yield exactly `346` owners over exactly the twelve
   panel images with exactly `343` greedy-eligible;
3. the split is not exactly six discovery and six confirmation images as frozen
   in contract item 12;
4. any query group's full prefix does not end at `BOX_START`, or its tail is
   not exactly equal to that category's sealed variable-length canonical
   suffix;
5. any owner does not carry exactly seventeen logical roles, a physical
   candidate is created by any means other than collapse of those roles within
   `(image, normalized_description)`, or a query group holds more than one
   request per unique coordinate tuple;
6. a per-owner proposal probability appears in any artifact, or a
   category-conditioned score is named as one;
7. more than two image shards are quarantined;
8. a confirmation statistic is computed with any rule object or calibration
   receipt whose digest differs from the sealed discovery one, or calibration
   reads any confirmation row;
8a. a support decision is derived from a rank or margin rather than from
   calibrated `peak_lift` and `local_concentration`, a `q05`/`q25` band or a
   category-stratified threshold is used as primary, or a
   `pooled_underrepresented` category receives a changed threshold;
8b. `epsilon` is adjusted away from `0.002` (single-context) or `0.004`
   (cross-context) on the strength of observed parity;
9. an owner labelled `never_frontier_tested` is reported as having no
   localization support, or a persistent negative is assigned to an owner that
   is not `greedy_eligible`, is a native true positive, or has an undercovered
   bank; or such an owner enters a false-negative prevalence or confirmation
   denominator;
10. an interpretation would require a causal claim, a visual-tower-information
    claim, a raw cross-image log-probability comparison, evidence from a failed
    shard, or a pre-P0 score or threshold; or
11. loop-tail contexts would enter a prevalence statistic on the same footing
    as ordinary contexts;
12. a score row lacks a covering `admission_receipt_id`, or an admission is
    reused across contexts, categories, or channels; or
13. any model call on the scoring model omits explicit `position_ids`, or a
    query group reuses another group's cache state.

Nonpositive or ambiguous evidence closes unresolved. No causal, coverage,
absence, or architecture claim is permitted from this unit.
